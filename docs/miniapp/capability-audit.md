# Telegram Mini App capability audit

This audit compares the Harnessgram control panel with the current [official Mini Apps API](core.telegram.org/bots/webapps). The implementation keeps authentication and CSP unchanged, sends no new data to the server, and treats every Telegram API as optional for older clients.

| Capability | Official documentation | Used before this audit? | Recommendation | Done in this PR? |
| --- | --- | --- | --- | --- |
| Back button, OS back and edge-swipe | [BackButton](core.telegram.org/bots/webapps#backbutton), [web app back event](core.telegram.org/api/web-events#web-app-setup-back-button) | Yes, including a shared browser-history stack for tabs, disclosures, sheets, dialogs and embedded apps. | Keep the native button visible whenever the reversible stack is non-empty. Browser/OS edge-back and the Telegram button must unwind the same stack; home alone may close the app. Guard this behavior in a real browser. | Yes. Added an explicit all-inner-screens regression guard; the existing controller already covered sheets and dialogs. |
| Safe area and content safe area | [SafeAreaInset and ContentSafeAreaInset](core.telegram.org/bots/webapps#safeareainset) | Partial: Telegram safe-area CSS variables protected top/bottom chrome, but content insets were incomplete and the two top insets were added together. | Use the larger relevant inset, protect both inline edges and the bottom, and react when either inset changes. | Yes. CSS now consumes both official variable families without double-padding, and layout propagation reacts to both change events. |
| Optional fullscreen | [requestFullscreen, exitFullscreen and fullscreenChanged](core.telegram.org/bots/webapps#initializing-mini-apps) | No. Embedded app frames may use HTML fullscreen, but the panel does not request Telegram fullscreen. | Offer fullscreen only for an immersive viewer with a visible exit. Do not force it for a control panel. | No. There is not yet a sufficiently valuable immersive panel screen; forced fullscreen would be a regression. |
| Theme, viewport, activation lifecycle | [Events available for Mini Apps](core.telegram.org/bots/webapps#events-available-for-mini-apps) | `themeChanged` and browser visibility were handled; Telegram viewport/activation events were not. | Reflow embedded-app safe-area layout on viewport changes. Stop polling while deactivated and refresh immediately on activation. | Yes. `themeChanged` remains in place; viewport, safe-area, `activated` and `deactivated` are now handled. |
| Haptic feedback | [HapticFeedback](core.telegram.org/bots/webapps#hapticfeedback) | Yes, broadly: light impacts for actions, selection feedback for navigation/disclosures, and success/warning/error notifications for outcomes. | Continue using haptics only at meaningful interaction and outcome boundaries. | Already complete; no blanket document-level haptic was added. |
| MainButton and SecondaryButton | [BottomButton](core.telegram.org/bots/webapps#bottombutton) | No. | Consider a native primary action only on a stable single-action screen. Decision lists can contain several approvals and notes, so a global native button would be ambiguous and could cover navigation. Use native progress if such a screen is introduced. | No; unsafe/ambiguous in the current multi-card screens. |
| Native popup and confirm | [showPopup and showConfirm](core.telegram.org/bots/webapps#initializing-mini-apps) | No. The panel uses accessible sheets and deliberate two-tap arming for destructive bulk actions. | Use native confirmation only for a short, context-free confirmation. Preserve in-page confirmation where details, counts, undo, or typed state must remain visible. | No; replacing the current contextual flows would remove information and produce inconsistent fallbacks. |
| Per-viewer preference storage | [CloudStorage](core.telegram.org/bots/webapps#cloudstorage), [DeviceStorage and SecureStorage](core.telegram.org/bots/webapps#devicestorage) | Local/session storage remembers the selected view, read markers and disclosure state. | DeviceStorage is appropriate for non-sensitive UI preferences when the client population supports it; CloudStorage would synchronize UI state across devices but makes a user preference remotely stored. Keep fallback storage and avoid migrating read markers without a product decision. | No. The “no new data sent” constraint rules out CloudStorage in this change, and asynchronous migration of established preferences is not risk-free. |
| Add to home screen | [addToHomeScreen and checkHomeScreenStatus](core.telegram.org/bots/webapps#initializing-mini-apps) | No. | Expose only from an explicit install/help affordance after product design; never prompt on launch. | No; unsolicited installation UI is not a control-panel convenience. |
| Prepared-message sharing | [shareMessage](core.telegram.org/bots/webapps#initializing-mini-apps) | No. | Add only after the bot creates an approved prepared message and the owner explicitly chooses Share. | No; it needs a new server-side prepared-message flow and would violate this PR's data boundary. |
| Orientation lock | [lockOrientation and unlockOrientation](core.telegram.org/bots/webapps#initializing-mini-apps) | No. | Keep orientation adaptive for the dashboard. Lock only during a future media/fullscreen experience and always unlock on exit. | No; the responsive panel benefits from rotation. |
| Version and feature guards | [isVersionAtLeast](core.telegram.org/bots/webapps#initializing-mini-apps) | Yes for versioned APIs, with feature checks for optional methods and objects. | Every new API call/event must have an API-version or feature guard and retain a web fallback. | Yes. New 8.0 lifecycle/safe-area events are version-gated; viewport handling is feature-gated. |

## Security and compatibility notes

No endpoint, request body, authentication behavior, `initData` validation, script origin, frame permission, or Content Security Policy changed. Safe-area behavior is CSS-first, so clients that do not define Telegram variables resolve them to zero. Lifecycle events are additive: older clients retain the existing Page Visibility polling behavior.
